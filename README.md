<h1 align="center">Atlas Terminal</h1>

<p align="center">
  Терминал для Android-головных устройств с ADB, Telnet и локальным shell-доступом
</p>

Atlas Terminal объединяет выполнение shell-команд, быстрые пресеты, историю и экспорт лога в
одном интерфейсе для автомобильных головных устройств. Доступны локальный `adbd`, совместимый
Telnet-режим с автоматическим поиском shell, а также локальный `/system/bin/sh` и
пользовательский shell.

> Терминал выполняет команды с теми правами, которые вы выбрали. ADB-команды могут
> изменить системное состояние устройства. Проверяйте команду до запуска.

## Интерфейс

Главный экран объединяет статус подключения, консоль с цветным выводом, конструктор префикса и
поле команды. В отдельных вкладках доступны быстрые команды и настройки ADB, shell-процесса,
размера шрифта, автопрокрутки и временных меток.

## Возможности

- подключение к ADB по адресу и порту; готовые режимы Atlas (`5555`), Preface (`7777`) и Custom;
- автоматический поиск локального Telnet shell;
- отдельные цели выполнения: ADB Shell и `sh`;
- ограниченный таймаут выполнения с закрытием зависшего транспорта или процесса;
- цветной вывод shell/ANSI/logcat/getprop-подобных строк;
- история последних команд, навигация по истории и экспорт лога;
- встроенные диагностические и системные пресеты с возможностью добавлять свои команды;
- сохранение ADB-ключа в приватном no-backup хранилище приложения;
- адаптивная иконка Atlas в общем graphite-стиле семейства приложений.

## Безопасность

Опасные готовые команды `mount`/`remount` удалены из пресетов и быстрых prefix-чипов. Произвольные
команды, введённые вручную или сохранённые пользователем, приложение намеренно не переписывает.
Оставшиеся системные пресеты (`am kill-all`, изменение global settings, `logcat -c` и мягкий
перезапуск zygote) также могут менять состояние устройства и требуют проверки перед запуском.

## Требования

- Android 8.0 или новее (API 26+);
- для ADB — доступный локальный или сетевой `adbd`;
- для локального `sh` — доступный `/system/bin/sh`;
- JDK 17 и Android SDK 36 для сборки.

## Установка и запуск

1. Установите подписанный APK на головное устройство.
2. Откройте «Настройки», включите `ADB helper` и выберите режим подключения.
3. Для ADB укажите адрес и порт; для Telnet оставьте режим Telnet — приложение самостоятельно
   ищет локальный shell endpoint.
4. Для локального выполнения выберите цель `sh`.
5. На вкладке «Терминал» выберите цель выполнения, введите команду и нажмите «Выполнить».
6. На вкладке «Пресеты» используйте диагностическую команду или добавьте собственную.
7. Перед экспортом или очисткой лога при необходимости включите отображение временных меток.

ADB-ключ генерируется при первом использовании и хранится в `noBackupFilesDir`; его приватная
часть не выводится в лог и не входит в APK.

## Сборка и проверка

Требуются JDK 17 и Android SDK 36. Используйте Gradle Wrapper из репозитория:

```sh
ANDROID_HOME=/path/to/android-sdk sh gradlew verify :app:assembleDebug
```

Задача `verify` запускает JVM unit tests и Android lint. Debug APK создаётся в
`app/build/outputs/apk/debug/`.

Для release-сборки нужен локальный игнорируемый `secure.signing.gradle` и keystore. В этом
рабочем наборе signing-конфигурация использует тот же release-сертификат, что и AtlasCodecFix;
секретные файлы не являются частью исходников и не должны добавляться в Git:

```sh
ANDROID_HOME=/path/to/android-sdk sh gradlew \
  -Pbranch.name=main verify :app:assembleDebug :app:assembleRelease
apksigner verify --verbose --print-certs \
  app/build/outputs/apk/release/*.apk
```

На `main` используется базовый `versionName` и увеличивается только базовая версия релиза.
На другой ветке базовые значения не меняются: к `versionName` добавляется очищенное имя ветки,
и оно же отражается в имени APK. Шаблон артефакта:
`<effectiveVersionName>[<versionCode>]AtlasTerminal-release.apk`.

В checkout без Git-ветки используется суффикс `-detached`; для канонической release-сборки можно
явно передать `-Pbranch.name=main`.

## Совместимость и ограничения

- unit tests и lint не заменяют проверку на реальном head unit;
- ADB-порт и Telnet shell необходимо подтвердить на целевом устройстве;
- OEM-ограничения, доступность локальных shell-процессов и поведение overlay/launcher могут
  отличаться между прошивками;
- выполнение команд зависит от выбранного транспорта и прав процесса, поэтому успешное открытие
  соединения не означает, что конкретная команда будет разрешена системой.
